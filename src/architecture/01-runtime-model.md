# 运行时模型——代码跑在哪、怎么通信

## 核心约束：两台机器，一根网线

整个 Web 开发的复杂性，根源只有一个物理事实：

> 代码跑在两个完全不同的地方——用户的浏览器和你的服务器。它们之间没有任何共享内存，只有一根不可靠的网线。

这意味着：

- **浏览器端的代码不能直接访问数据库**。如果可以，任何一个网站都可以读取你的银行账户。浏览器是一个"受控环境"——它给你有限的 API（DOM、Fetch、localStorage），但拒绝你访问文件系统和任意端口。
- **服务器端的代码不能直接画界面**。服务器没有屏幕，它只能返回数据（HTML、JSON、图片）。画界面的工作永远在浏览器端。
- **两者之间的每次通信都是一次网络往返**。网络有延迟、可能丢包、可能断开。你不能假设"调用了就会立刻返回"。

### 这对架构意味着什么

从"两台机器一根网线"出发，每一层 Web 架构的存在都有物理原因：

```
约束：一台机器只能暴露有限端口
    → 需要 Nginx 做统一入口

约束：网络传输有延迟，重复传输浪费带宽
    → 需要压缩（gzip）、缓存（CDN）、合并请求（打包）

约束：浏览器只能运行 JavaScript
    → 需要 TypeScript/JSX 编译成 JavaScript

约束：浏览器不能存数据
    → 需要后端 + 数据库

约束：浏览器和服务器语言不同，怎么保证数据格式一致
    → 需要 HTTP 协议 + JSON 序列化
```

理解了这个根本约束，你会明白：**没有一项 Web 技术是"因为开发者觉得这样更好"而存在的——每一项技术都是因为物理现实逼着你这么做。**

3. 后端进程不直接暴露给公网——只监听 `localhost:3001`，只有 Nginx 能访问
4. 数据库也不暴露给公网——只监听 `localhost:5432`
5. 静态文件（前端编译产物）由 Nginx 直接从磁盘返回，不过后端进程

## 第一层：浏览器——代码运行在用户电脑上

### 浏览器不是一个"显示工具"

许多人误以为浏览器只是"把 HTML 画成漂亮的页面"。实际上，浏览器是一个**完整的应用程序运行平台**。它包含：

| 子系统 | 做什么 | 你的代码怎么用它 |
|--------|--------|-----------------|
| **JS 引擎（V8 / SpiderMonkey / JavaScriptCore）** | 解析并执行 JavaScript 代码 | 你写的每一行 JS/TS 代码最终都在这里执行 |
| **渲染引擎（Blink / WebKit / Gecko）** | 解析 HTML/CSS，构建 DOM 和 CSSOM，计算布局，绘制像素 | 你写的每个 `<div>` 都会变成一个 DOM 节点，每个 CSS 属性都会参与布局计算 |
| **网络栈** | 建立 TCP 连接、TLS 握手、发送 HTTP 请求、处理 WebSocket | 你调用的每次 `fetch()` 都由网络栈执行 |
| **存储** | Cookie、localStorage、sessionStorage、IndexedDB | 你的登录状态、用户偏好，存在用户的电脑上 |
| **Web APIs** | 定时器（setTimeout）、地理定位、通知、剪贴板、摄像头 | 浏览器暴露给 JS 的系统能力 |

### 浏览器的安全边界——为什么前端不能直接操作数据库

浏览器是一个沙盒。你在网页中写的 JavaScript，不能：

- 直接读写用户的文件系统（除非用户主动选择文件）
- 直接访问任意 IP 地址和端口（受同源策略限制）
- 读取用户的剪贴板（除非用户主动粘贴）
- 启动系统进程
- 访问 `<input type="file">` 以外的本地文件

**这是故意的。** 如果任何网页都能读写你的 `~/.ssh/id_rsa`，互联网在第一天就会崩溃。

### 浏览器的同源策略

这是浏览器安全模型的核心。一句话概括：

> 一个网站（`https://example.com`）上的 JavaScript，只能访问同源（同协议、同域名、同端口）的 API。访问其他域名需要对方明确允许（CORS 头）。

这意味着如果你在 `example.com` 的页面上执行 `fetch("https://evil.com/steal")`，浏览器会阻止这个请求——除非 `evil.com` 的服务器在响应头中明确写了"允许 example.com 访问我"。这就是 CORS（跨域资源共享）。

## 第二层：网络——请求如何从浏览器到达服务器

### DNS 是什么——不只是"域名翻译成 IP"

**DNS (Domain Name System) 是三重身份的统一体**：

| 身份 | 是什么 |
|------|--------|
| **一个协议** | DNS 协议定义了"查询域名记录"的报文格式——客户端发查询包，服务器回复响应包，走 UDP 53 端口（大响应走 TCP） |
| **一个分布式数据库** | 全球几万台 DNS 服务器共同存储了所有域名的记录，没有一台服务器存全部——通过层级委托分散存储 |
| **一套基础设施** | 根服务器、顶级域服务器、权威服务器、递归解析器、缓存——协同工作的一套系统 |

**DNS 的查询过程**：

```
你在浏览器输入 https://example.com。浏览器不认识"example.com"——它需要 IP 地址。

example.com 是什么 IP？
    │
    ▼
查浏览器 DNS 缓存（之前访问过这个域名）
    │ 没找到
    ▼
查操作系统 DNS 缓存（本地 hosts 文件也在这里查）
    │ 没找到
    ▼
查本地 DNS 解析器（如 systemd-resolved 在 127.0.0.53:53）
    │ 没找到
    ▼
查 ISP 的 DNS 递归解析器（如 8.8.8.8 / 1.1.1.1）
    │ 没找到缓存
    ▼
ISP 的解析器逐级向上查询：
    │
    ├── 问根服务器："谁管 .com？"
    │   根服务器回复：".com 由 Verisign 管，它的 IP 是 x.x.x.x"
    │
    ├── 问 Verisign（.com 顶级域服务器）："谁管 example.com？"
    │   Verisign 回复："example.com 的权威 DNS 服务器在 ns1.namecheap.com"
    │
    └── 问 ns1.namecheap.com（example.com 的权威 DNS 服务器）："example.com 的 IP 是什么？"
        权威 DNS 回复："example.com 的 A 记录是 203.0.113.5"
    │
    ▼
ISP 递归解析器把结果（203.0.113.5）返回给你的电脑，并缓存一段时间
整个过程：几十毫秒到几百毫秒。层层缓存后，第二次访问同一域名几乎瞬间。
```

**为什么查询链是"浏览器缓存→系统缓存→本地解析器→ISP→逐级向上"这个顺序？**

因为 DNS 是一个**分布式的、逐级授权的层级系统**。没有一个"全球 DNS 服务器"存储所有域名——那样单点会瘫痪。相反，域名空间被从右向左逐级委托：

```
. (根)              ── 全球 13 组根服务器，存储"哪个机构管 .com"
  │
  ├── .com (顶级域)  ── Verisign 管理，存储"哪个 DNS 管 example.com"
  │
  └── example.com   ── 你自己在注册商的 DNS，存储"example.com → 哪个 IP"
```

查询从缓存开始是为了效率——如果浏览器缓存里已经有了，就省去后面所有步骤。

**ISP 是什么？**

ISP（Internet Service Provider，互联网服务提供商）就是你付网费的公司——中国电信、中国联通、Comcast、Singtel。它们不仅给你提供物理网络连接，还运行 DNS 递归解析器让你能解析域名。你每次上网，流量先经过 ISP 的网络，才到互联网。

### 域名授权层级——凭什么这些机构有权力

域名授权是一个**合同链**，不是政府权力：

```
ICANN (互联网名称与数字地址分配机构)
  │ 全球域名的最高管理机构——1998 年从美国商务部独立的非营利组织
  │ 被全球互联网社区认可为域名系统的协调者（不是执法者，没有政府身份）
  │
  ├── 授权：和注册局签合同——"你可以管理 .com 这个顶级域"
  │
  ▼
注册局 (Registry)——每个顶级域只有一个
  │
  ├── .com / .net     →  Verisign（美国公司，合同管理）
  ├── .org            →  PIR (Public Interest Registry)
  ├── .cn             →  CNNIC (中国互联网络信息中心)
  ├── .uk             →  Nominet
  ├── .io             →  ICB (Internet Computer Bureau)
  └── .dev, .app      →  Google (通过 ICANN 的 gTLD 计划获得)
  │
  │ 授权：和注册商签合同——"你可以向公众售卖 .com 域名"
  │
  ▼
注册商 (Registrar)——直接面向消费者的销售渠道
  │
  ├── Namecheap, GoDaddy, Cloudflare Registrar, 阿里云(万网), 腾讯云
  │
  │ 销售：你付 ~$10-15/年，获得 example.com 一年的使用权
  │
  ▼
注册者 (Registrant)——你
  在注册商的 DNS 面板上添加 A 记录：example.com → 203.0.113.5
  全世界任何地方解析这个域名，最终都会得到这个 IP
```

**关键理解**：
- ICANN 不是政府——它通过合同授权注册局，合同的法律效力来自注册局自愿遵守
- 注册局不能自己卖域名——必须通过注册商（防止垄断）
- **你买的不是域名本身——是域名一年的使用权**。每年续费。不续费 → 域名被释放 → 别人可以注册
- DNS 面板上的 A 记录和域名注册是两个独立操作——你先注册域名（向注册商），再配 DNS 记录（在注册商的 DNS 面板上）

### IP 分配层级——更严格的层级链

**域名的获取和 IP 的获取完全是两条独立的链，互不影响。** 你可以注册一个域名但不给它配 IP（没人能访问），也可以有一台有公网 IP 的服务器但没有域名（只能通过 IP 地址直接访问）。

```
域名链：ICANN → 注册局 → 注册商 → 你 → 得到域名（一个名字）
IP 链：  IANA  →  RIR   → ISP/云厂商 → 你 → 得到 IP（一个地址）

这两条链在物理上毫无关系。当你给域名配置一条 A 记录（指向你服务器的 IP），
你是在"把一个名字和一个地址关联起来"——但这个关联是你手动创建的。
```

**IP 分配链详解：**

```
IANA (Internet Assigned Numbers Authority)
  │ 全球 IP 地址的最高管理机构——ICANN 的下属机构
  │ IPv4 地址总量：约 43 亿个（2³²）
  │ IANA 不直接分配 IP 给最终用户
  │
  ├── 把 /8 块（每个 ~1670 万个 IP）分配给 RIR
  │
  ▼
RIR (Regional Internet Registry)——5 个，各管一个地理区域
  │
  ├── APNIC   → 亚太地区（含中国、日本、印度、澳大利亚）
  ├── ARIN    → 北美地区（美国、加拿大）
  ├── RIPE NCC → 欧洲、中东、中亚
  ├── LACNIC  → 拉丁美洲和加勒比地区
  └── AFRINIC → 非洲
  │
  │ 把 /12 ~ /16 块（几千到几万个 IP）分配给 ISP 和大型网络
  │
  ▼
ISP (互联网服务提供商) / 云厂商 / 大型企业
  │
  ├── 中国电信、中国联通、中国移动 → 分配给家庭宽带用户（你的"个人 IP"）
  ├── AWS, 阿里云, Google Cloud → 分配给云服务器（你的 VPS 的"公网 IP"）
  └── 大型机构 (MIT, Google 等) → 分配给自己的内部网络
  │
  ▼
最终用户
  ├── 家庭宽带用户 → ISP 分配一个动态公网 IP（重启路由器可能变）
  ├── VPS 客户 → 云厂商分配一个固定公网 IP（你的服务器 IP）
  └── 企业网络 → 内部用私有 IP（192.168.x.x, 10.x.x.x），出口时共用少量公网 IP（NAT）
```

**IPv4 地址的剩余量**：IPv4 地址在 2011 年 IANA 级别耗尽，2019 年欧洲 RIPE 也耗尽。现在获得 IPv4 地址的唯一方式是**从现有持有者手里租/买**——云厂商从它们的库存中分配给你，你付月费。IPv6 有 2¹²⁸ 个地址（340 万亿万亿万亿），不存在耗尽问题。

### 公网 IP vs 私有 IP vs 局域网 vs NAT

**公网 IP（Public IP）**：在互联网上全球唯一的地址。全世界任何机器都可以通过这个地址直接访问你的设备。

**私有 IP（Private IP）**：仅在局域网内部有效。互联网上的机器不能直接通过私有 IP 访问你的设备。私有 IP 范围（RFC 1918）：

| 范围 | 常见用途 |
|------|---------|
| 10.0.0.0 — 10.255.255.255 | 大型企业内部网络 |
| 172.16.0.0 — 172.31.255.255 | 中型企业内部网络 |
| 192.168.0.0 — 192.168.255.255 | 家庭路由器（你的 WiFi 网络） |

当你家里连接 WiFi 时，每个设备（手机、笔记本、iPad）**都有一个私有 IP**——比如 `192.168.1.5`。但这些设备不能直接用这个 IP 访问互联网——因为 `192.168.1.5` 在全球有几百万人同时在用。

**NAT（Network Address Translation）** 解决这个问题：

```
你的笔记本电脑（私有 IP: 192.168.1.5）
    │ 要向 google.com 发请求，但私有 IP 不能直接上网
    ▼
家庭路由器（私有 IP: 192.168.1.1，公网 IP: 123.45.67.89）
    │ 路由器把源地址从 192.168.1.5"翻译"为 123.45.67.89
    │ 同时记录"这个连接来自 192.168.1.5"
    ▼
Google 服务器（看到请求来自 123.45.67.89）
    │ 回复发给 123.45.67.89
    ▼
家庭路由器（根据之前的记录，把回复转给 192.168.1.5）
```

**这就是为什么你家里的笔记本"有 IP 但没有公网 IP"——你家里的所有设备共享路由器这一个公网 IP，通过 NAT 转换上网。** 你的笔记本不能在公网上被直接访问——因为公网只看到路由器的 IP，看不到你笔记本的私有 IP。

**住宅 IP 和服务器公网 IP 的区别**

| | 住宅 IP | 服务器公网 IP（数据中心 IP） |
|------|--------|--------------------------|
| 来源 | ISP 分配给你家的宽带连接 | 云厂商从它们申请的 IP 段中分配给你的 VPS |
| 动态还是固定 | 通常动态（重启路由器可能变） | 通常静态（你的 VPS 一直用同一个 IP） |
| 信誉 | 很多网站认为住宅 IP = 真实用户 | 很多网站对数据中心 IP 有额外限制（反爬虫、验证码） |
| 能否跑服务器 | 技术上可以，但多数 ISP 的条款禁止 | 可以——这就是它存在的目的 |
| 成本 | 包含在宽带费中 | 按小时/月付（静态 IP ~$3-5/月） |

### 域名 vs IP——两条独立链的关联点

```
域名获取：  ICANN → 注册局 → 注册商 → 你 → example.com
IP 获取：   IANA → RIR → 云厂商 → 你 → 203.0.113.5

关联点：    你在 DNS 面板上创建 A 记录：example.com → 203.0.113.5
           ↑ 这一步是手动关联的，不是自动的 ↑
```

**这两个系统独立意味着**：
- 你可以有 IP 而没有域名（访问 http://203.0.113.5 直接看到你的网站）
- 你可以有域名而没有 IP（买了域名没配 A 记录，访问会 DNS 解析失败）
- 你可以把域名指向任何你控制的 IP（迁移服务器时只改 A 记录，域名不变）
- 域名被释放 ≠ IP 被释放——各自遵循各自的到期规则

### 端口到底是什么

端口不是物理的——**它是一个 16 位数字（0-65535），存在于 TCP/UDP 数据包的头部**。

```
TCP 数据包的结构：
┌──────────────────┬──────────────────┬──────────────────────┐
│ 源 IP (32位)      │ 目标 IP (32位)    │ 数据负载               │
│ 源端口 (16位)     │ 目标端口 (16位)   │ (HTTP 请求的实际内容)   │
└──────────────────┴──────────────────┴──────────────────────┘
```

当操作系统收到一个数据包，它看"目标端口"字段——比如 80——就知道应该把这个包交给**监听 80 端口的那个进程**。如果没有任何进程监听这个端口，内核直接丢弃数据包并回复"连接被拒绝"。

**端口由谁分配？**

- 程序**请求**操作系统："我想监听 3001 端口"
- 操作系统**核实**没有其他进程正在用 3001 端口
- 分配成功 → 这个程序就是"3001 端口的拥有者"，直到它退出

```
# 你的程序调用（Go 为例）：
net.Listen("tcp", ":3001")

# 操作系统：
# 1. 检查 3001 端口是否空闲 → 是
# 2. 创建内核 socket 对象，绑定到 3001 端口
# 3. 返回文件描述符给进程
# 4. 当 TCP 数据包到达（目标端口 = 3001）→ 内核把数据写入这个 socket → 进程读取
```

**端口范围约定**：

| 范围 | 用途 |
|------|------|
| 0-1023 | 系统端口——只有 root 才能监听（HTTP=80, HTTPS=443, SSH=22, DNS=53） |
| 1024-49151 | 注册端口——任何用户可以监听（PostgreSQL=5432, Redis=6379, 你的 App=3001） |
| 49152-65535 | 临时端口——操作系统为出站连接随机分配（浏览器连接你的服务器时，源端口来自这个范围） |

**端口不是"物理的线"**——它是一个放在数据包里的数字。操作系统用这个数字把数据包路由到正确的进程。这就是它的全部。

### 服务器相关概念速查

| 概念 | 是什么 | 你付什么钱 |
|------|--------|-----------|
| **物理服务器** | 一台有 CPU、内存、硬盘、网卡的真实机器 | 硬件费 + 电费 + 带宽 |
| **VPS** | 物理机上用虚拟化技术分出的独立 OS 实例 | 月费 ~$5-200 |

## 第三层：服务器入口——Nginx / 反向代理

### 为什么必须有一个入口？

你的服务器有一个公网 IP。当请求 `https://example.com` 到达这个 IP 时，端口默认为 443（HTTPS）或 80（HTTP）。

**一台机器上只有一个 443 端口和一个 80 端口。** 如果你有两个后端服务（Node.js 在 3001、Go 在 3002），它们不能同时监听 443——端口冲突。

这就是为什么需要 Nginx。**Nginx 是 443 和 80 端口的唯一占有者。它根据请求的域名和路径，决定转发给哪个内部端口。**

### Nginx 的配置模型

Nginx 配置的核心是两个概念：

**Server Block**：按域名分流
```
如果请求的 Host 是 api.example.com → 进入 api server block
如果请求的 Host 是 app.example.com → 进入 app server block
```

**Location Block**：按路径分流（在同一个域名下）
```
如果路径是 / → 返回静态文件
如果路径是 /api/ → 转发到 Node.js 3001
如果路径是 /admin/ → 转发到 Go 3002
```

一个典型的单域名多服务配置：

```nginx
# 所有 HTTP 请求先跳转 HTTPS
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

# HTTPS 入口
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    # 静态文件（前端构建产物）
    location / {
        root /var/www/frontend;
        try_files $uri /index.html;
    }

    # API 请求 → Node.js 后端
    location /api/ {
        proxy_pass http://localhost:3001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 管理后台 → Go 服务
    location /admin/ {
        proxy_pass http://localhost:3002;
    }
}
```

### Nginx 还做了什么（不止转发）

| 功能 | 为什么需要 |
|------|-----------|
| **HTTPS 终结** | 证书配置在 Nginx 一次，后端服务之间走 HTTP——简单且快 |
| **静态文件服务** | 前端 JS/CSS 由 Nginx 直接从磁盘返回，零额外开销。后端进程不用处理静态文件请求 |
| **压缩（gzip）** | Nginx 在返回前压缩文本响应，减少传输量 |
| **限流** | 防止单个 IP 过量请求，保护后端 |
| **负载均衡** | 多个后端实例时，Nginx 把请求均匀分发 |
| **安全隔离** | 后端只监听 `127.0.0.1`（仅本机），外部无法直接攻击 |

## 第四层：后端应用——请求在服务器上被处理

### 后端进程收到请求后做了什么

```
请求到达你的 Node.js 进程（localhost:3001）

1. 解析
   读取 HTTP 请求：方法 GET、路径 /api/users、头部 Authorization: Bearer xxx

2. 路由匹配
   GET /api/users → 匹配到 UsersController.list()

3. 中间件链（执行顺序：声明顺序）
   认证中间件：验证 JWT token → 解析出 user_id
   权限中间件：检查 user_id 是否有 "read:users" 权限
   日志中间件：记录请求方法、路径、耗时
   ← 以上任何一个中间件可以拦截请求（返回 401/403）或放行

4. 业务逻辑
   调用 Service 层：根据查询参数构建 SQL
   调用 Repository 层：执行 SQL 查询 → 拿到结果行

5. 序列化
   把数据库行转为 JSON：[{id:1, name:"Alice"}, {id:2, name:"Bob"}]

6. 返回响应
   HTTP/1.1 200 OK
   Content-Type: application/json
   [{"id":1,"name":"Alice"},{"id":2,"name":"Bob"}]
```

这个过程在任何语言、任何框架中都是相同的——只是实现细节不同。Go 的 HTTP handler、Python 的 FastAPI route handler、Node.js 的 Express middleware——它们处理的都是同一种流水线。

### 服务器上的进程生态

一台生产服务器通常运行着这些进程：

```
其中：    
公网 IP: 203.0.113.5

进程分布：
  Nginx          → 监听 0.0.0.0:80 和 0.0.0.0:443（公网可访问）
  Node.js API    → 监听 127.0.0.1:3001（仅本机可访问）
  Go 后台服务     → 监听 127.0.0.1:3002（仅本机可访问）
  PostgreSQL     → 监听 127.0.0.1:5432（仅本机可访问）
  Redis          → 监听 127.0.0.1:6379（仅本机可访问）
  
  systemd        → 管理上述所有进程的启动、停止、重启
  logrotate      → 定期清理日志
  fail2ban       → 监控登录失败，封禁可疑 IP
```

**所有这些进程都是独立的**——各自独立的内存空间、独立的生命周期。如果 Node.js 进程崩溃，systemd 会自动重启它，而 Nginx 和 PostgreSQL 不受任何影响。这就是操作系统进程隔离的价值。

### 后端和数据库之间怎么通信

后端进程通过**数据库驱动**（也叫客户端库）与数据库通信：

```
Node.js 代码：db.users.findMany({ where: { orgId: 42 } })
    │
    ▼
Prisma（ORM）：把 JS 对象调用翻译成 SQL
    │
    ▼
pg（PostgreSQL 驱动）：通过 TCP 连接发送 SQL 到 localhost:5432
    │
    ▼
PostgreSQL 进程（监听 5432）：解析 SQL → 查询执行计划 → 读取磁盘 → 返回行
```

后端进程和数据库通常在同一台机器或同一个内网中——不会暴露给公网。它们通过不同的端口通信（5432 是 PostgreSQL 的默认端口，6379 是 Redis 的默认端口）。

## 第五层：响应回程——数据回到浏览器

### 响应怎么返回

```
后端进程返回 JSON
    │
    ▼
Nginx 收到（localhost:3001 → Nginx）
    │
    │ Nginx 可选操作：
    │ - gzip 压缩（减少传输量）
    │ - 添加/修改响应头（Cache-Control, CORS）
    │ - 限速
    │
    ▼
通过 TLS 加密 → TCP 传输 → 互联网 → 到达用户电脑
    │
    ▼
浏览器网络栈接收 → TLS 解密 → 交给 JS 引擎
    │
    ▼
你的 await fetch() 拿到 JSON 对象
```

### 浏览器收到数据后发生了什么

```
JS 拿到 JSON：[{id:1, name:"Alice"}, {id:2, name:"Bob"}]
    │
    ▼
调用 setUsers(data)（React state 更新）
    │
    ▼
React 重新渲染组件 → 生成新的 JSX
    │
    ▼
Virtual DOM diff → 计算最小 DOM 变更
    │
    ▼
更新真实 DOM：添加两个 <li>Alice</li> 和 <li>Bob</li>
    │
    ▼
浏览器重新布局 + 重新绘制 → 用户在屏幕上看到更新
```

### 而页面一开始是怎么出现的

用户刚打开 `https://example.com` 时，浏览器收到的第一个响应是 HTML，不是 JSON：

```
浏览器请求 GET /
    │
    ▼
Nginx 返回 index.html（从 /var/www/frontend/ 读取）
    │
    ▼
浏览器解析 HTML → 发现：
  <link href="/static/css/main.css"> → 发起请求下载 CSS
  <script src="/static/js/main.js">   → 发起请求下载 JS
    │
    ▼
CSS 下载完成 → 构建 CSSOM
JS 下载完成 → V8 执行 → React 渲染初始界面
    │
    ▼
React 在 useEffect 中调用 fetch("/api/users") → 发起 API 请求
    │
    ▲
    └── 回到本文的"第一层：浏览器"——一个完整的闭环
```

## 运行时全景图（总结）

```
用户输入 URL → 按回车

    │                    ┌────────────────────────────┐
    ▼                    │  DNS 解析                    │
┌─────────┐              │  example.com → 203.0.113.5  │
│ 浏览器   │              └────────────────────────────┘
│         │  ──HTTPS──▶  ┌────────────────────────────┐
│ JS 引擎  │              │  Nginx（入口，监听 443）       │
│ 渲染引擎 │              │  ├ / → 返回静态 HTML/JS/CSS   │
│ 网络栈   │              │  ├ /api/* → localhost:3001   │
│         │  ◀─────────  │  └ /admin/* → localhost:3002  │
└─────────┘              └────┬───────────┬───────────┘
                              │           │
                  ┌───────────┘           └──────────┐
                  ▼                                   ▼
          ┌──────────────┐                  ┌──────────────┐
          │ Node.js:3001 │                  │ Go:3002       │
          │ 路由→中间件   │                  │ 路由→业务逻辑  │
          │ →业务→响应    │                  │ →响应         │
          └──────┬───────┘                  └──────────────┘
                 │
        ┌────────┴────────┐
        ▼                 ▼
  ┌──────────┐     ┌──────────┐
  │PostgreSQL│     │  Redis   │
  │  :5432   │     │  :6379   │
  └──────────┘     └──────────┘

整个链路中，每个箭头都是一次网络通信。
除本地回环(localhost)外，每次通信都有延迟、可能失败、需要重试。
Web 架构的所有复杂性，都是在管理这个"分布式系统的物理现实"。
```

## 你的理解验证

在结束本章前，对照一下你对运行时的理解是否准确：

> "浏览器接收 URL 后顺着 DNS 缓存链条找到 IP，然后连接服务器获取前端的 HTML/CSS/JS 编译结果（静态文件），浏览器渲染出页面。交互时通过 API 调用后端进程，后端连接数据库等处理后返回数据，前端 JS 拿到数据后更新页面。"

✅ 完全正确。三个细节补充：

1. **"获取编译结果"**——浏览器下载的是**已经编译好的** JavaScript/CSS，不是你写在 `.tsx` 里的 JSX。编译发生在 `npm run build` 时，不在浏览器请求时

2. **"通过 API 调用后端进程"**——API 不是一种特殊的技术。它就是"发送 HTTP 请求到某个 URL 路径，这个路径对应后端的一个处理函数"这个约定的名字。你在前端代码里写 `fetch("/api/users")`，浏览器发起 HTTP 请求，Nginx 把这个请求转发给后端进程，后端处理并返回 JSON

3. **前端代码中的 API 调用可以指向同一个服务器的后端进程（`/api/xxx`），也可以指向完全不同的服务器（`https://api.other-server.com/xxx`）**——浏览器不关心后端在哪，它只关心"这个 URL 返回了数据"

> "前端就是用 HTML + CSS + JS 三种语言组织"

✅ 但需要补充：在现代前端开发中，HTML/CSS/JS 通常以**组件**为单位混在一起（如 React 的 `.tsx` 文件里有 HTML 样式的 JSX 和 CSS 引入），然后**构建工具**把它们拆回三种独立的产物，分别发送给浏览器。最终浏览器看到的确实是 HTML + CSS + JS——但你的开发过程中看到的组织方式和最终产物不是一回事。详见 [02 构建与编译全景](02-build-and-compile.md)。

> "后端进程就是写好的程序，编译后运行在服务器上，或解释型语言在解释器中运行"

✅ 完全正确。
